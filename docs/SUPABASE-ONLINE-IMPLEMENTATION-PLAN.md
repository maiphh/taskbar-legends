## MVP user behavior

Preserve local play, local save export/recovery, zoom/audio, and existing management features.

Login creates or loads a fresh server account for the authenticated user. Never upload the existing local snapshot, wallet, items, farm proofs, RNG or client timestamps into a verified account. Show a short explanation that the local account is preserved separately. Sign out returns to the preserved local account and runs its existing restore path once. Cloud data is cached under a separate user-specific key and never overwrites `taskbar-legends:v1:party-v2`. A network error during online play does not silently switch the account to local authority: keep the last authoritative snapshot, freeze economic controls, and show retry/reconnect. Missing configuration produces a useful Settings state, not startup failure. Only public project information goes in Vite variables. Service role secrets never enter Vite, the Tauri bundle, logs, source control or responses.

## Phase 2: durable schema, atomic commit and retry protocol

Use one migration under `supabase/migrations/` with a minimal account aggregate plus normalized item ownership:

- `game_accounts`: `user_id uuid` primary key references auth.users, `revision bigint`, `rules_id`, `state jsonb` excluding wallet/inventory, `gold bigint`, `tickets bigint`, server `checkpoint_at timestamptz`, fractional tick remainder, `active_until timestamptz`, optional server paused flag, `pending_job_id uuid`, created/updated timestamps. Nonnegative currency/revision constraints. Keep the existing core roster/equipment/pity/progression/accrual in state for this MVP rather than inventing a second core schema.
- `game_items`: `(user_id,item_id)` primary key, validated item JSON/essential slot/rarity fields as convenient, owner FK, no global uniqueness assumption for existing seed-derived IDs. Cross-owner equip is impossible because only the server reconstructs a user's inventory. Inventory cap and equipment references are checked by core parse before commit.
- `game_requests`: `(user_id,request_id)` unique, canonical payload SHA-256, kind, status, base/result revision, result/summary JSON, timestamps. A retry of the same ID+hash returns its stored outcome; another payload with the same ID returns409. Use canonical serialization before hashing, not arbitrary property insertion order. Keep durable receipts; do not expire economic replay protection after a short cache TTL.
- `game_jobs`: job ID, owner, request ID/hash, base revision, fixed target server timestamp, remaining active tick work, offline interval work, working state, cursor/version, status and lease token/expiry if needed. Only required for multi-chunk work below; keep the working state isolated from the published account.

RLS enabled on every table. No anon/authenticated INSERT/UPDATE/DELETE policies or write grants to economic tables. Prefer private server-only tables and API-only account access; if authenticated SELECT is provided, restrict it to `auth.uid()=user_id` and avoid exposing raw job/receipt details unnecessarily. Backend RPCs are revoked from PUBLIC/anon/authenticated and granted only to service_role. Use schema-qualified identifiers, fixed safe search_path, and the minimum definer privileges. Service-role-only RPC arguments may include the trusted handler's derived user ID and generated result, never directly client-submitted account data.

Implement transactional `begin_operation`, `save_job_chunk`, and `commit_operation` RPCs (names flexible). Begin locks account row and obtains database transaction time. It checks existing receipt before expectedRevision, so a successful retry still returns success after revision changes. It checks the expected account revision, creates one pending job/receipt with fixed target time, and prevents other economic operations from overtaking it. Chunk saves use expected cursor/version/lease so duplicate consumers cannot advance RNG twice. Commit locks the account, checks owner/job/base revision, reconstructs the validated final aggregate, replaces only that user's items, writes wallet/state/checkpoint/presence/revision and durable receipt atomically, then clears pending job. The transaction rolls back entirely on failure. Do not commit the wallet then save inventory in separate HTTP calls.

An idempotent bootstrap can be a separate RPC using insert-on-conflict. Business rejections (not enough gold, invalid hero/item, full lock cap, etc.) should return a durable final outcome. Time settlement before an otherwise invalid command can be committed with an explicit rejected-command receipt; define this consistently so time is never rewarded twice or lost on retry.

## Phase 3: server time, active progression and lazy offline accrual

Use one server checkpoint per account, shared across devices. DB time captured by begin_operation defines an immutable target. The client never chooses the amount of elapsed time or proof of a clear. Before every equip, upgrade, party change, recruit, chest choice, or other mutation, settle the old loadout/rules over the interval first, then apply the command. This prevents a newly equipped item or newly earned farm proof from applying retroactively to past time.

Support verified active play with a short **server-issued activity lease**, initially15seconds, renewed by authenticated sync every3–5seconds while the main game is visible/running. Store `active_until`, not a browser timestamp. To settle from checkpoint to captured server now: run the shared deterministic `step` only over the segment covered by the prior activity lease; treat the uncovered remainder as offline time using the existing aggregate `applyOffline`, capped at8hours. Tick fractions are carried once. At most15seconds/300ticks of active work normally accumulate; no simulation of eight hours of battle ticks is required. Active lease grace after disconnect is expected and bounded. Two devices can renew the same lease, but cannot create two timelines. A client repeatedly sending presence merely causes the server to run the real authorized simulation.

For explicit Pause, settle first, record server pause state, and stop issuing active work until Resume. Choose and document a single policy: recommended MVP global account pause freezes accrual while paused; Resume advances the checkpoint over that paused interval without granting it. Show that account-wide effect in the control label. Hidden/disconnected accounts with no explicit pause receive aggregate offline rewards after their active lease expires. Do not silently conflate pause with a connection loss.

`applyOffline` must operate only on server-produced farm proofs/RNG/state. Reuse its fractional chest/gold/XP/ticket logic and earned-stage eligibility. Preserve the8h cap and advance checkpoint to captured now even if only8h is granted, preventing repeated capped claims. Do not repeatedly call it on arbitrary small chunks in a way that resets chest caps or changes the reward distribution: calculate the offline interval once after active work completes and persist its completed result with the job cursor. A claim/sync is itself idempotent. Compare projections can be read-only and must not trigger settlement more than the defined sync operation.

All current valuable commands work: retry boss/frontier, pull, pullMany1/10, autoEquip, autoParty/presets, upgrade, equip, chooseChest, party swaps, gear lock, hero preset lock. Use extracted pure ManagementAuthority validation or a shared command service rather than two drifting legality implementations. No partially accepted ten-pull: validate affordability, execute all ten deterministically in the working copy, and commit one receipt/revision. Audio/zoom/placement remain local preferences and bypass cloud economic commands safely.

### Bounded work under Edge CPU limits

Benchmark the exact generated bundle with several seeds, early/late stage fights,15s active intervals,8h offline claim with maximum chest work, and ten-pull. Supabase has2s CPU/request, not2s wall. Set a conservative initial chunk size (e.g.100ticks), measure it, and target comfortably below the CPU limit. Use fixed tick counts rather than elapsed wall-time checks inside the deterministic core. Never trust a client-supplied tick count.

If the operation exceeds the safe per-invocation budget, persist only its private working job state and return202 `{jobId,status:'pending'}`. The client polls/continues the same job with backoff; each request advances at most one safe chunk. No queue deployment is necessary for this MVP. Any authenticated device for that account may resume the pending job; different mutations receive pending/busy rather than race past it. All target timestamps, request payloads and final command are immutable. There is no published half-claimed balance, and polling does not extend the job's target. Crashes resume from the last CAS-protected chunk; only the final transactional commit publishes rewards and the new lease. Bound maximum jobs/work/input and provide retry diagnostics rather than discarding pending work.
