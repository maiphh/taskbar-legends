# Default compact party runtime and removal of deprecated gameplay

Date: 2026-11-16. Base: main `c6926e0`. No repository `AGENTS.md` was found. This is a focused runtime cleanup, not an asset/history purge.

## Outcome

Opening `/` with no query immediately runs the current compact party game: centered hero loadout, item stash and hero strip, Formation, mana signatures, complete attack-at-contact playback, compact preferences, browser docked management, and native controls/management windows. There is one gameplay mode and one presentation shell. Remove deprecated alternate game/expanded canvas management paths and preview activation plumbing; merely defaulting the two flags to true is insufficient.

Keep unrelated useful controls (`?shot`, native-menu screenshot variant, v14/salvage simulation settings, `view=management` / `view=control` internal routing). The latter are actual native window entry routes, not deprecated gameplay modes. Preserve opaque native window fallback and shell lifecycle; an OS presentation fallback is not the old game.

## Entry and shell cleanup

- `src/main.ts`: delete `partyV2Preview` / `compactPreview` query gates and legacy branches. Initialize compact prefs and viewport unconditionally, create the current account unconditionally, show Menu, and route all gameplay actions through `ManagementAuthority`. Browser-only dock/resize differences still depend on native presence, not a gameplay switch. Remove preview titles/notices and mode-matching URL errors. Rename the CSS class `compact-preview` to a neutral shell name or apply the compact rules directly; keep the real compact styling.
- `src/bootstrap.ts`: retain its three-way main / native management / native controls entry dispatch.
- Delete `party-preview.html` and `src/party-preview-bootstrap.ts`; remove the `partyPreview` Rollup input from `vite.config.ts`. Keep index, management, control build inputs. Old `?combat=party-v2&compact=1` URLs may harmlessly display the same game because those query keys are ignored; remove their parser, links and test dependencies. Do not keep a redirect-only preview entry.
- `src/platform/desktop/tauri.ts`: always start `startCompactDesktop`; remove the old noncompact `DesktopController` polling implementation and its `__shell` diagnostics surface if no current consumer remains. Preserve lifecycle hooks, fail-safe behavior, quit/relaunch and shell-mode handling in the current compact runtime. `compact-runtime.ts` already understands overlay vs opaque window. Remove `controller.ts` if now unreferenced; retain `math.ts` because compact geometry/runtime directly imports its types and monitor schema.
- `src-tauri/src/shell.rs`: remove `party_preview` from `ShellState`, CLI detection, URL override, and relaunch argument propagation. Launch `index.html` normally and use compact resize behavior by default. Remove the preview relaunch test. Keep `--opaque-window`, saved shell preferences, tray controls, and native management/control windows and IPC. Avoid deleting the useful `shell_mode` command: compact-runtime still invokes it. Update the native configuration default dimensions only where they still describe the retired expanded mode (opaque currently opens800x488; use the current compact defaults consistently).

## One core constructor and resolver

- Make `createState` directly construct the current party account with `combatRules:'party-v2'`, current starter party `mw2/mw1/priest`, the same deterministic starter gear used by the live game, and one initial `beginEncounter`. Remove the old create-legacy-then-reset flow. Remove `createPartyState` and update its callers rather than retain two semantic constructors. Optional test fixtures may explicitly omit starter gear if they need an empty inventory; the shipped default must match today's desired game.
- `src/core/combat.ts`: keep current party/enemy spawning and encounter setup; remove the legacy `hit`, `heal`, `attackHero`, enemy walk/cooldown loop and old spawnWave branch. `combatTick` calls `partyCombatTick` directly. Retain any shared exported damage utility only if a current caller uses it.
- `core/economy.ts`: always use party family profiles, preset formation, party gear utility, and current auto-equip. Remove legacy role-based stats/autoParty/autoEquip alternatives and `combatRules` guards. Preserve ordinary economy/rewards, item lock/protected salvage, deterministic IDs, and progression.
- `core/game.ts`, `core/events.ts`, `core/party-combat.ts`, `management/authority.ts`: remove legacy runtime conditions, leaving their current party branch. Preserve presentation-completion gates, timeout ordering, native combat event clocks, mana commit behavior, boss-repeat minimum-cycle padding, and active statuses/effects/projectile paths still used by current encounters. Remove legacy hero passive implementations that now immediately return for party-v2, and cooldown code only used by that retired branch; do not delete enemy specials or their cooldowns.
- Retain the serialized `combatRules:'party-v2'` literal as a format identifier if useful. It must no longer select a resolver. Current runtime states always carry it; legacy missing-field compatibility, if retained, belongs at the decode boundary only. Use current party enemy validation everywhere. Do not delete old version support for stable item IDs, historical balance numbers, or failed-save quarantine just because the old game loop is removed.

## Persistence: existing current-game accounts take priority

Continue using **`taskbar-legends:v1:party-v2`** as the canonical storage key. This directly resumes the user's current game at `/`; renaming to the old global key risks overwriting another account and adds unnecessary migration. Keep a clearly named exported constant for the canonical key if useful. The suffix can remain a storage identifier even after removing preview terminology from UI. Preserve the `:failed` quarantine/export/discard flow on this canonical key.

Do not merge or overwrite the separate legacy `taskbar-legends:v1` account automatically. Existing current-game data wins when both exist. When only the legacy key exists, show a brief explicit notice that the previous account is preserved and this version uses the current party account; offer export of that original legacy raw value through the existing export mechanism or Settings. Keep the old raw key untouched. An automatic conversion of old mid-fight actions and offline cadence is not needed to activate the current game safely and would enlarge this cleanup substantially. A new current account must never be mistaken for successful migration of the old account. This small read/export boundary is compatibility data handling, not a retained legacy runtime.

For explicit import of old saves, either implement a tested durable-data migration or reject with an actionable export-preserved explanation; do not silently reinterpret missing combatRules into current live units. Preferred focused scope is to accept existing party saves unchanged and reject incompatible legacy gameplay snapshots clearly. Keep v1 item-ID migration for party-compatible imported data where applicable. The failed-save UI must preserve raw data on rejection and prevent autosave over the rejected source. Remove the current instruction to open a matching gameplay URL because that URL no longer exists.

## Remove the obsolete canvas management UI, retain used presentations

`PixelUI` is not entirely obsolete. `Renderer` uses it for lane drawing, text/material helpers, damage/event feedback, and offline welcome; `ManagementView` instantiates it for recruit reveal (`ensureReveal` around line300). Blindly deleting `pixel-ui.ts` would break current features.

Remove the expanded canvas management branches, old HUD islands, panel toggle/scroll/roster input handling, and private `drawHeroes`, `drawGear`, `drawRecruit`, `drawUpgrades`, `drawSettings` paths now superseded by DOM `ManagementView`. Retain compact lane/edit rendering, shared drawing helpers used by the surviving lane/reveal/welcome, recruit results, welcome presentation, fonts, atlas readiness, and necessary hit controls. Extract reveal helpers if that makes deletion clearer, but avoid a gratuitous broad rewrite. Remove associated old panel geometry and CSS only when unused by current presentation; retain the separate recruit reveal geometry.

`Renderer`: always compact field/viewport and party positioning/animation/event clocks. Delete legacy enemy truncation, old movement attack-animation fallback, expanded island field calculations, and old camera behavior alternatives. Keep current complete clip timing and formation screen anchors.

Update debug `openPanel` to open/select the DOM management workspace if current screenshot tools need it; otherwise replace it with a clear current management debug API and update all callers. Do not keep legacy canvas panel code just to satisfy old screenshot scripts. Preserve snapshot/seed, clock/reveal, asset-error, management, and compact diagnostics needed by current tools.
