## Phase 0 design and implementation

### Save migration policy

Continue accepting v1 saves through the existing deterministic v1-to-v2 migration and v2 saves through existing strict validation. A future combat rules migration must have an explicit version discriminator, convert an in-progress encounter only at a documented boundary, retain campaign/economy/roster/inventory/pity/reward state, and invalidate incompatible combat-rate samples. Preserve the source bytes before migration or overwrite. A decode/validation error is not an empty slot: copy raw bytes to `${saveKey}:failed`, retain the primary bytes, and block writes until the player exports or explicitly discards the failed save. If writing quarantine storage fails, retain the untouched primary and block writes in-session; a later load retries quarantine. Quarantine survives reload and is not cleared by routine autosave.

### User recovery flow

An incompatible or corrupt save displays a persistent accessible recovery panel. The player can download the raw save as JSON or explicitly discard it and start a new save. The normal restore catch does not replace the game state with a saveable fresh slot. The overlay native cursor hit-test includes the modal recovery surface so its controls remain clickable in click-through mode. Storage access errors are surfaced in the panel status notice.

## Phase 3 implementation and validation

Party rules remain opt-in at `http://127.0.0.1:5173/?combat=party-v2` (compact UI: `&compact=1`) and use the isolated save key `taskbar-legends:v1:party-v2`. Normal browser/native accounts still use legacy rules. `createState`, legacy party selection/equipment behavior, legacy enemy IDs/lookups, and checked-in design/simulation JSON were not migrated or edited.

`src/core/party-definitions.ts` validates all 18 configured hero IDs and their basic/active/passive mappings. Seven IDs have the explicit initial kits; the other eleven inherit documented closest-kit templates and retain their rarity/stat modifiers. `heroStats` uses family profiles for party-v2 only; raw derived intervals keep the existing configured minimum of 8 ticks and all legacy values remain unchanged. Party throughput, preset DPS ranking, comparison, and auto-equip use `max(attackTicks, 6)` to reflect the 4-tick windup plus 2-tick minimum recovery.

`src/core/party-combat.ts`, `party-effects.ts`, and `party-enemies.ts` implement the shared impact batch, strongest/capped effects and shield-provider attribution, nonrecursive success counters, at-impact fourth-shot/ramp behavior, single-secondary deterministic cleave, fixed-center ground projectiles, and party-only assassin/bomber/boss patterns. Buff, weaken, and shield effects commit before that tick's damage batch regardless of attack/heal animation kind; healing remains after survival resolution. Basic-vs-active identity is serialized on launched projectiles, so enemy ranged basic hits advance boss patterns at actual contact. Marked area attacks remain interruptible caster windups and cancel at caster death; released ground projectiles remain independent. New encounter start clears old-clock effects/projectiles before resetting native time. The legacy enemy enum and CONFIG enemy lookup remain unchanged.

Party management adds Balanced/Fast farm/Boss sustain presets, `partyLocked` on deployed heroes, authority-validated lock toggles, role-aware selection from derived stats, and front-to-rear placement that preserves locked positions. Auto-equip evaluates cloned owned-hero equipment records, scores actual candidate stats using throughput/EHP/support weights `(1,.25,.1)`, `(.2,1,.7)`, and `(.25,.5,1.2)`, scores the same full owned roster before and after so bench donor baselines cancel while equipped donor loss remains, commits only positive gains with stable hero/item ties, and stops after 128 passes. The documented support output is healing coefficient per cooldown/realized basic cycle times ATK, ATK-scaled buff/debuff uptime, max-HP-scaled shields, and max-HP-scaled intercept coverage. Party and gear comparison DPS share the actual repeatable basic damage coefficient (including the Priest's 0.7 healthy-target fallback) and realized action cycle. Management displays preset coverage, lock controls, player-facing effect descriptions, cycle-aware basic rate, correctly formatted percentage gear values, and party utility gain. Gear comparisons and scoring do not mutate live units or consume RNG.

`tests/party-encounter-matrix.test.ts` reproducibly generates `docs/COMPACT-PARTY-PHASE-3-MATRIX.json`. It runs 105 deterministic cases across stages 1/11/19 and levels/stars 1/1, 10/2, and 20/4, with the same three common gear slots per deployed hero and inherent rarity/modifiers retained. It compares seven compositions against grunt, archer, bomber, assassin, and chapter-one boss pressure. Enemy HP and ATK are doubled after stage scaling for this explicit stress matrix; this is not a live wave balance estimate.
